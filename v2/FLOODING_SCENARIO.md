# 대규모 Flooding 테스트 시나리오 설계

> 작성 2026-10-26, 지도 조회 7패턴 모델 기준으로 수치 갱신 2026-10-27. 확률·배수·시간은 **초기 가정**이며, 실측 또는 운영 로그가 생기면 교체한다.
> 기준 코드: `loadtest-scenarios/real/lib/api.js`(경로·상태 판정 `RULES`), `loadtest-scenarios/real/cuj.js`, `loadtest-scenarios/real/lib/stomp.js`, `loadtest-scenarios/real/lib/slo.js`
> 실행 절차와 기존 단계는 `loadtest-scenarios/real/README.md`를 따른다.

설계 순서: **1. 트래픽 패턴 가정 → 2. 테스트 목표 → 3. 테스트 시나리오 → 4. 부하 프로파일 → 5. 확인 필요**

이 문서의 TPS는 HTTP 요청 수 기준 RPS(초당 요청 수)를 뜻한다. 채팅 메시지는 WebSocket으로 따로 센다.

## 대규모 부하테스트 트래픽 패턴 가정

이동 목적형 서비스는 날씨와 주변 행사에 따라 스파이크성 트래픽이 생긴다. 이 장에서는 그 배수를 벤치마크에서 가져와 피크 RPS를 정한다.

### **1.1 벤치마크 배수**

공개 자료의 수치다. 도시·서비스·연도가 달라 **절대값이 아니라 배수 범위**로만 쓴다.

| 벤치마크 | 확인된 패턴 | 시나리오 반영 |
| --- | --- | --- |
| 카카오택시 호출 분석 | 2016년 여의도 벚꽃·폭우·불꽃축제일에 택시 수요가 공급의 **2.7~4.4배**. | 지역 수급 부족과 미배차를 재현한다. **4.4배는 수요/공급 비율이며 TPS 증가 배수가 아니다.** |
| 카카오모빌리티 장마철 분석 | 장마철에는 호출이 늘고 운행 기사가 줄어 수급 불균형이 커진다. | 탐색·매칭 요청과 실패 후 재시도를 함께 본다. 재시도 횟수는 **내부 가정**이다. |
| Didi 콘서트 사례 | 2024년 공연장 주변 호출 수요가 전주 대비 **314% 증가**. | 고부하 참고값 **4.14배**(= 1 + 3.14). |
| Didi 2026년 행사 주문 자료 | 평일 대비 콘서트 주변 주문 **88% 증가**, 스포츠 행사 주변 **185% 증가**. | 행사 1단계 **1.88배**, 2단계 **2.85배**. |
| 콘서트 차량 호출 연구 | 퇴장 이동의 약 **70%가 종료 후 1시간 안에** 발생. | 종료 직후 60분을 집중 관찰 구간으로 둔다. 구간 내 분배(10분 40%, 10~60분 30%)는 **내부 가정**이다. |

### **1.2 기준값과 피크 RPS**

기준은 README의 평시 피크 **91 RPS**다. 배수를 곱해 피크 RPS를 구한다.

| 구간 | 배수 | 피크 RPS | 근거 |
| --- | --- | --- | --- |
| 평시 피크 | 1.00× | 91 | README 기준선 |
| 행사 1단계 | 1.88× | 약 171 | 콘서트 주문 증가 |
| 행사 2단계 | 2.85× | 약 259 | 스포츠 행사 주문 증가 |
| 행사 고부하 | 4.14× | 약 377 | 공연장 호출 증가 |
| Flooding 한계 탐색 | 약 5.6× | 512 | 벤치마크 최댓값을 넘는 구간 |
- 본 테스트는 **서비스 전체**에 배수를 적용하는 보수적 가정이다. 행사 구역 비중을 `f`로 두면 전체 피크는 `91 × (1 + f × (배수 − 1))`이다. `f`는 결정이 필요하다(5장).
- README의 기존 행사 피크 180 RPS는 1.98배로, 위 1단계(171)와 2단계(259) 사이다.

## 2. 테스트 목표 가정

### **2.1. 일반 부하테스트의 정상 기준 목표 (SLO)**

시스템이 정상적인 트래픽에서 얼마나 안정적으로 동작하는지, SLO를 지키는지 평가하는 것이 일반 부하 테스트이다. 

- 목표 TPS
- 최대 응답 시간
- CPU 사용률
- 메모리 사용률

`loadtest-scenarios/real/lib/slo.js`를 따른다.

| 지표 | 목표 | 판정 |
| --- | --- | --- |
| 가용성 | 99.9% | 미달 시 단계 실패 |
| 조회 응답 | p95 ≤ 1s, p99 ≤ 2.5s | 초과 시 임계 후보 |
| 쓰기·매칭 응답 | p95 ≤ 1.5s, p99 ≤ 3s | 초과 시 임계 후보 |
| WebSocket 연결 | 99.9%, 3초 안에 CONNECTED | 미달 시 임계 후보 |
| 메시지 전달 | 저장 99.9%, 전달 p99 ≤ 2s | 미달 시 임계 후보 |
| CUJ 완료율 | 97% | 미달 시 임계 후보 |
| 정합성 | 100% | 1건이라도 어긋나면 실패 |
| CPU | 평균 60% 이하 | 85% 이상 지속 시 포화. 60%는 ECS `cpu_target`, 85%는 **내부 가정** |
| 메모리 | 평균 75% 이하 | 85% 이상 지속 시 포화. **내부 가정**. 현재 설정에 메모리 목표는 없다 |

### **2.2 대규모 Flooding 테스트의 수용량과 임계점 목표**

대규모 Flooding 테스트의 경우 시스템이 극단적인 부하 상황에서 어떻게 반응하고 복구되는지 최대 수용량 파악과 임계점을 확인하고 검증하는 것에 목표를 둔다. 

- 최대 동시 접속자 수 및 초당 TPS의 한계
- 과도한 부하 상황에서 리소스에서 병목 지점 확인
- 확장 메커니즘 작동 여부
- 자가 복구까지 걸리는 Failback 시간

| 목표 | 정의 | 측정 |
| --- | --- | --- |
| 최대 동시 접속자 수 | 동시에 세션을 진행 중인 VU와 동시 WebSocket 연결 수 | 임계점 단계의 VU·연결 수 |
| 초당 요청 한계 | SLO를 모두 만족한 단계 중 성공 RPS 최댓값 | 단계별 성공 RPS |
| 임계점 | 위 임계 후보가 **연속 2분** 발생한 첫 단계 | 2분은 **내부 가정** |
| 병목 지점 | 임계점에서 가장 먼저 포화된 자원 | HikariCP active·pending(풀 10), MySQL 연결·잠금 대기, JVM GC, Redis Pub/Sub, nginx 429, RDS CPU |
| 확장 메커니즘 | 부하 증가 후 태스크 증설이 일어났는지, 얼마나 걸렸는지 | ECS 스케일 이벤트 시각, 증설 태스크 Ready 시각, 최대 태스크 도달 여부 |
| Failback 시간 | 부하를 낮춘 뒤 정상으로 돌아오기까지 걸린 시간 | 아래 2.3 |

### **2.3 Failback 정의**

- 부하를 평시 수준으로 낮춘 시점부터, **오류율 0.1% 이하와 p95 SLO 이내가 2분 연속** 유지된 시점까지를 잰다. 0.1%와 2분은 **내부 가정**이다.
- 복구 중 미처리 쓰기 요청(대기 큐)과 WebSocket 재연결 수를 함께 기록한다.
- 행사 종료 후 60분 관찰 구간 안에 끝나지 않으면 실패로 기록한다.

### **2.4 확장 설정 참고**

`v2/locals.tf`의 서비스별 설정은 CPU 목표 60~70%, 최대 태스크 2~6개다. scale-out 쿨다운은 60초, scale-in 쿨다운은 300초다. WebSocket 서비스는 scale-in을 끈다. CPU 기반 확장은 반응이 느리므로, 증설이 늦게 일어나면 그 자체를 결과로 기록한다.

## 3. 테스트 시나리오

### **3.1 사용자 세션 흐름**

사용자 세션은 실제 사용자 행동처럼 시스템에서 발생하는 주요 작업들을 시뮬레이션할 수 있도록 세션 흐름을 구체화하는 것이 필요하다. 

#### 1. 목적과 범위

행사 시점에 몰리는 트래픽을 재현하기 위해 **가상 사용자 한 명의 세션**을 정의합니다. 대상은 지도 핀 조회, 상세 조회, 모집·요청 작성, 매칭, 채팅, 운행 시작입니다.

#### 2. 공통 실행 규칙

| 항목 | 규칙 |
| --- | --- |
| 이동 | 화면 너비(좌우) 또는 높이(상하)의 약 60% |
| 확대·축소 | 줌 레벨 ±1단계 |
| 일반 이동 사이 간격 | 핀을 살펴보는 시간. **(제안)** 3~8초 균등 분포 |
| 빠르게 위치 찾기 | 짧은 간격으로 연속 조작. **(제안)** 0.3~1초 |
| 시작 좌표 | 가상 사용자마다 행사장 주변에서 무작위로 분산하고 지터를 줌. 같은 좌표에 몰리지 않도록 함 |
| 패턴 선택 | 평시 또는 행사 비중에 따라 확률적으로 선택 |

#### 3. 지도 조회 패턴 (7종)

| 패턴 | 조작 순서 | 평시 | 행사 | 핀 조회 수 |
| --- | --- | --- | --- | --- |
| 현재 위치 확인 | 진입 → 핀 확인 → 종료 | 20% | 10% | 1 |
| 좌우 비교 | 진입 → 우 → 우 → 좌 | 20% | 15% | 4 |
| 행사장 주변 탐색 | 진입 → 우 2회 → 상 1회 → 확대 → 축소 | 20% | 30% | 6 |
| 밀집 지역 자세히 보기 | 진입 → 확대 2회 → 우 → 상 | 15% | 20% | 5 |
| 넓은 지역 훑기 | 진입 → 축소 → 좌 → 하 → 확대 | 10% | 10% | 5 |
| 이동 후 원래 지역 복귀 | 진입 → 좌 → 상 → 우 → 하 | 10% | 10% | 4* |
| 빠르게 위치 찾기 | 진입 → 우 2회 → 상 1회 (연속) | 5% | 5% | 2* |
- 평시와 행사 비중은 각각 합계 100%입니다.
- 가중 평균 핀 조회 수는 **평시 약 3.95건/세션, 행사 약 4.5건/세션**입니다. 행사 시 세션당 조회가 늘어나는 것이 핵심 부하 증가 요인입니다.
- 표의 `*` 항목은 다음 규칙으로 계산한다.
  - 시작 영역으로 돌아온 조작은 캐시 히트로 보고 재조회하지 않는다. 이동 후 원래 지역 복귀는 조작 4회 중 조회 4건이다(진입 1 + 조작 3).
  - 빠르게 위치 찾기는 연속 조작 중 중간 영역을 조회하지 않고 마지막 영역만 조회한다. 진입 1 + 최종 1 = 2건이다.
- 조작 사이 think time은 일반 패턴 3~8초, 빠르게 위치 찾기 0.3~1초다.
- 구현 위치: `loadtest-scenarios/flooding/config/map-patterns.js`(패턴·비중), `lib/map-plan.js`(조회 규칙). `dry-run.js`가 위 수치를 검증한다.

```
세션 시작 / 로그인 상태 확인 (사전 발급 테스트 토큰)
  └─ 지도 진입 → 현재 영역 핀 조회
       ├─ 지도 조회 패턴 1종 선택 (7종, 평시·행사 비중 다름)
       ├─ 각 이동·확대·축소 후 해당 영역 핀 조회 (3.1 조회 규칙 적용)
       └─ 핀이 있으면 선택 여부 결정 (핀이 없으면 상세 단계 생략)
  └─ 핀 선택 및 상세 조회: 60% (전체 세션 기준)
       ├─ 조회만 하고 종료: 60%
       ├─ 핀 게시글 작성: 10%
       ├─ 동행 모집 글 작성: 10%
       ├─ 기존 동행 모집에 참여: 15%
       └─ 택시팟 매칭 요청: 5%
  └─ 동행 참여·모집 또는 택시팟 매칭 성공 시
       └─ 채팅방 진입: 80%
            ├─ 채팅 조회만 수행: 25%
            └─ 메시지 1~3건 작성: 75%
                 ├─ 참여자 채팅방 나가기: 30%
                 └─ 참여 유지: 70%
                      └─ 출발 조건을 충족한 팟의 방장이 운행 시작

```

### **3.2 행위별 요청 매핑**

| 사용자 행동 | 요청·처리 | 확인할 결과 |
| --- | --- | --- |
| 로그인 상태 확인 | `GET /api/users/me` | 인증 성공률, 지연 |
| 지도 진입·이동 | `GET /api/map-pins`, 필요 시 `GET /api/nearby-posts` | 이동 횟수에 따른 조회 RPS |
| 핀 상세 확인 | 동행 `GET /api/companion-posts/{id}`, 커뮤니티 `GET /api/community-posts/{id}` | 상세 p95·p99 |
| 핀 게시글 작성 | `POST /api/community-posts` | 생성 성공, 조회 가능 여부 |
| 동행 모집 글 작성 | `POST /api/companion-posts` | 게시글·모집자 참여·채팅방 생성 정합성 |
| 기존 모집 참여 | `POST /api/companion-posts/{id}/participants` | 정원 초과 방지, 참여 성공률 |
| 택시팟 매칭 요청 | `POST /api/taxi-pots` → `GET /api/users/me/current-taxi-pot` → `GET /api/taxi-pots/{id}` | 기존 팟 합류·신규 생성 비율, 중복 매칭, DB 잠금 |
| 채팅 참여·작성 | 채팅방·메시지 조회 → WebSocket 연결·구독·전송 | 연결 성공률, 전달 지연 |
| 채팅방 나가기 | WebSocket 종료. 팟을 떠나면 `DELETE /api/companion-posts/{id}/participants/me` 또는 `DELETE /api/taxi-pots/{id}/participants/me` | 연결 해제와 참여 인원·상태 일치 |
| 운행 시작 | 방장이 `PATCH /api/taxi-pots/{id}` 또는 `PATCH /api/carpools/{id}` | 상태 전이, 스케줄러 처리 지연 |

### **3.3 세션당 요청 수와 조회 규모 (7패턴 모델)**

3.1의 흐름과 확률로 계산한 기대값이다. 채팅 메시지는 WebSocket이라 제외한다.

| 항목 | 평시 (normal) | 행사 (event) | 계산 |
| --- | ---: | ---: | --- |
| 인증 `GET /api/users/me` | 1.00 | 1.00 | 세션마다 1회 |
| 지도 조회 (패턴 가중 평균) | 3.95 | 4.50 | 3.1 표의 가중 평균 |
| 상세 조회 | 0.60 | 0.60 | 세션의 60% |
| 쓰기 분기 | 0.36 | 0.36 | 게시글 0.06 + 모집 0.12 (POST + 채팅방 목록) + 참여 0.09 + 택시 0.09 (POST + 현재 팟 + 상세) |
| 채팅 진입 REST | 0.29 | 0.29 | 채팅 진입 세션 0.144 × 2 (방 상세 + 메시지 목록) |
| 채팅 나가기 | 0.02 | 0.02 | 참여·택시 0.12 × 진입 80% × 메시지 작성 75% × 나가기 30% |
| **합계** | **6.22** | **6.77** | |

- 1,000세션 기준(평시): 지도 조회 약 3,950건, 상세 약 600건, 동행 참여 약 90건, 택시팟 요청 약 30건, 채팅 진입 약 144건이다.
- 계산 가정: 모든 요청 성공, 핀 존재, 근처 모집 핀 존재(없으면 `join_no_target`으로 집계).
- 이전 값(세션당 약 4.0, 1,000세션당 조회 약 1,900건)은 0/1/2회 이동 모델 기준이라 더 이상 쓰지 않는다.

## 대규모 부하 테스트 프로파일

### 1) 가상 사용자 수(VU)

VU는 실제 사용자의 활동을 시뮬레이션하여 동시에 세션을 진행하는 것으로 시스템에 부하를 주는 가상 사용자 수다. 

Little's Law로 계산한다 

```
VU ≈ 세션 도착률 × 평균 세션 시간
```

평균 세션 시간은 **60초 가정**이다. 지도 조작은 세션당 평균 3.15회(행사 3.70회)이고, 행동 사이 think time은 3~8초(평균 5.5초)로 잡았다. 실측으로 교체한다.

k6에서는 도착률(`constant-arrival-rate`)을 고정하고 VU는 결과로 보는 것이 맞다. 최대 VU는 계산값의 약 1.2배로 둔다.

| 단계 | 목표 RPS | 혼합 | 세션당 HTTP | 세션 도착률(/s) | 동시 VU(계산) | 최대 VU 설정(약 1.2배, 50 단위) |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 평시 피크 | 91 | 평시 | 6.22 | 14.6 | 878 | 1,050 |
| 행사 1단계 | 171 | 행사 | 6.77 | 25.3 | 1,516 | 1,820 |
| 행사 2단계 | 259 | 행사 | 6.77 | 38.3 | 2,296 | 2,750 |
| 행사 고부하 | 377 | 행사 | 6.77 | 55.7 | 3,341 | 4,000 |
| 한계 탐색 | 512 | 행사 | 6.77 | 75.6 | 4,538 | 5,450 |

- 세션 도착률 = 목표 RPS ÷ 세션당 HTTP, 동시 VU = 도착률 × 60초다.
- 채팅 WebSocket 동시 연결은 `도착률 × 0.108(메시지 작성 세션) × 120초(채팅방 체류, 내부 가정)`다. 512 RPS 단계에서 약 980 연결이며, README의 행사 목표 1,800 연결과 맞지 않는다.

### 2) 부하 증가 단계 및 유지 시간

| 단계 | 목표 RPS | 램프 | 유지 | 측정 구간 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 워밍업 | 91 | 5분 | - | 제외 | 커넥션·캐시 안정화 |
| 1 | 171 | 2분 | 10분 | 뒤 5분 | 행사 1단계 |
| 2 | 259 | 2분 | 10분 | 뒤 5분 | 행사 2단계 |
| 3 | 377 | 2분 | 10분 | 뒤 5분 | 행사 고부하 |
| 4 | 512 | 2분 | 10분 | 뒤 5분 | 한계 탐색 |
| 복구 | 91 | 2분 | 30분 | 전 구간 | Failback 측정 |

#### 부하 증가 단계: 불균등 간격

시스템에 점진적으로 부하를 가하기 위해 가상 사용자를 증가하는데 벤치마크 배수를 기반으로 증가 폭이 80~ 135 RPS 사이의 불균등 간격으로 증가한다. 

#### 부하 유지 시간: 단계 당 10분

설정한 목표 부하(TPS)를 일정 시간 동안 유지하여 시스템의 성능을 평가한다. 따라서 앞의 5분은 안정화를 위한 단계이고 뒤의 5분으로 판정한다.
